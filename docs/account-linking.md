# Account sign-in methods (MARKET-91)

Implementation and isolated checks are complete in the source checkout. The acceptance gate requiring disposable **real Google and password accounts on both web and native clients is still pending**. No production user was linked, no account was merged, no installed application was replaced, and no deployment or release is asserted by this receipt.

Signed-in, email-verified users open **Account → Sign-in methods**. The screen lists the providers linked to that Firebase user. It first verifies an existing method with `reauthenticateWithCredential` (password) or `reauthenticateWithPopup` (Google). Only a successful same-UID verification enables the separate add-method step. The reauthentication ticket lasts at most five minutes and authorizes one attempt. Password linking uses the authenticated user's existing email; the interface does not edit an email or search for an account by email.

Google linking invokes `linkWithPopup` directly from the add-method click, with an explicit popup resolver, fresh provider, account selector, and identity-only scopes. Password linking uses `EmailAuthProvider.credential` and `linkWithCredential`. The selected current user, SDK result, and active auth session must retain the original UID. The returned user must contain the target provider. No sign-in, account deletion, automatic collision recovery, or membership write is part of either link helper. Firebase rejects credentials already owned by another UID; the screen reports that collision and asks for fresh verification before another attempt. This follows the [Firebase account-linking contract](https://firebase.google.com/docs/auth/web/account-linking) and [reauthentication APIs](https://firebase.google.com/docs/reference/js/auth#reauthenticatewithpopup).

Project membership remains keyed by the existing UID. The account dialog refreshes the authenticated `/me` profile after linking and reconciles it without replacing the workspace client or edited source. A refresh failure is reported as **a committed method with an incomplete project refresh**, not as a failed link. It never unlinks a committed method or merges project records. Passwords remain only in transient form state and the Firebase credential operation; the current password is cleared after verification, and new-password fields are cleared after completion, failure, or unmount. Error messages use a fixed safe map rather than raw Firebase provider responses.

## Native browser handoff

The native client already has a Firebase user. Native add-method controls require the server auth configuration to explicitly advertise `account_link_available: true`; older services show an unavailable notice without opening a credential form or browser grant. Direct web linking continues through Firebase. Opening Account reloads linked-provider metadata so reopening after cancellation shows any method already committed in the browser. Adding either method opens the external browser rather than performing Google authentication inside the webview. It creates an authenticated five-minute grant containing that UID, the target provider, and a SHA-256 challenge. The existing fixed `open_desktop_login` command opens the grant URL; no arbitrary redirect is introduced.

The browser inspects the grant through an authenticated endpoint. A different UID receives a refusal before the linking form is rendered; **Use another account** permits an explicit sign-out and a fresh sign-in. The browser then performs the same existing-method reauthentication and same-user Firebase linking flow. It acknowledges completion to the grant. This acknowledgement is not proof of a credential mutation and grants no new access: the native client independently reloads its existing Firebase user and requires the target provider before refreshing that same user's ID token. **The link bridge never issues, exchanges, or signs in with a custom token.** Existing desktop sign-in grants keep their separate one-use custom-token behavior and cannot consume account-link grants.

Grant inspection, completion, exchange, and cancellation enforce the initiating UID. Exchange also requires the original verifier and consumes the grant once. Link grants have a transactional per-UID daily budget of 32; public desktop login keeps its separate budget. Neither passwords nor Google credentials cross the bridge. Cancel stops app polling, requests grant revocation, and prevents late app acknowledgement; it does not undo a credential already committed in the browser. A cancelled, consumed, or expired grant cannot be approved later.
